Figma 디자인 옮길 때 캡처보다 봐야 할 것

Figma 캡처만 보고 디자인을 매핑하면 단편 패치 로테이션에 빠진다. raw 디자인 컨텍스트로 spacing·color·font를 먼저 받고 코드를 짠 뒤 캡처로 검증해야 한다는 회고.

새 디자인이 떨어졌다. Figma 링크가 같이 왔다. 화면을 빠르게 보려고 노드 screenshot만 받았다. 캡처를 보면서 위에서부터 한 섹션씩 매핑했다.

결과를 사용자가 보고 어긋난 부분을 짚었다. 고쳤다. 다른 부분이 또 어긋났다. 또 고쳤다. 또 어긋났다. 사용자가 결국 짜증을 냈다.

원인은 정해져 있었다. 캡처는 픽셀 정밀도가 부족하다. 한 번 정리해 둘 만한 일이라 적는다.

캡처가 못 보여주는 것

화면 캡처를 보면 카드가 있고 디바이더가 있고 텍스트가 있다. 그런데 디바이더 두께가 1pt인지 0.5pt인지, 좌우 inset이 있는지 없는지, 색이 정확히 어떤 hex인지는 안 보인다.

더 큰 함정은 따로 있다. 카드와 카드 사이가 8pt 회색 갭인지 0pt 디바이더 라인인지가 화면에선 비슷해 보인다는 거다. 둘은 코드로 짜면 완전히 다른 구조다.

캡처를 보고 추측해서 코드를 짜면 결과는 비슷한데 실제 값은 다 다르다. 실 디바이스에서 보면 미묘하게 어긋난다.

raw 컨텍스트가 답이다

Figma MCP의 get_design_context는 해당 노드의 raw 정보를 다 내려준다. frame 별 width/height, padding, color hex, font name과 size, border radius, child 노드 계층 구조까지.

// 응답 예시 (60KB 가까이 옴)
"bg-white": ...                    // 배경색
"px-[20px] py-[12px]": ...         // padding
"text-[#241e17] text-[14px]": ...  // 색 + 폰트 사이즈
"border-b border-[#F2F2F2]": ...   // 디바이더
"size-[20px]": ...                 // 아이콘 크기

이걸 받아 두면 추측할 게 없다. 디바이더 색은 #F2F2F2, 카드 padding은 좌우 20pt 상하 12pt다. 화면 캡처로는 평생 모를 정보다.

캡처로 짠 코드의 실제 차이

내 코드는 디바이더 색을 coolGray200(약 #E0E0E0)로 잡았다. Figma 실제 값은 #F2F2F2였다. 색이 비슷해 보여도 결과가 미묘하게 어둡다. 카드 사이 갭도 8pt로 잡았는데 실제는 다른 값이었다.

이런 차이가 쌓이면 화면이 “그럴듯한데 정답은 아닌” 상태가 된다. 본인은 다 한 것 같은데 디자이너가 보면 한눈에 안다.

단편 패치 로테이션

캡처로 시작한 매핑은 단편 패치로 끝난다. 사용자가 “여기 디바이더가 다르다"고 짚으면 그 부분만 고친다. 그 옆에 또 다른 어긋남이 숨어 있는데 사용자가 다시 짚어주기 전엔 모른다. 한 부분 고치면 다른 부분이 깨진다.

이게 로테이션이다. 두세 바퀴 돌고 나면 어디까지 맞췄는지도 헷갈린다.

매핑 순서 비교

flowchart LR
  subgraph A["캡처 우선 (함정)"]
    A1[Figma 캡처] --> A2[추측 매핑] --> A3[코드] --> A4{어긋남?}
    A4 -- yes --> A5[부분 패치] --> A4
  end

  subgraph B["raw 우선 (정답)"]
    B1[get_design_context] --> B2[spacing/color/font 표] --> B3[한 번에 코드] --> B4[캡처로 검증]
  end

순서를 바꿨다

이렇게 한다.

  1. get_design_context로 노드 정보를 받는다.
  2. 응답이 크면 청크로 끝까지 다 읽는다. 중간에 추측 금지.
  3. 모든 spacing/color/font/디바이더 위치를 표로 정리한다.
  4. 그 표를 보고 코드를 한 번에 짠다.
  5. 매핑이 끝난 후에 화면 캡처로 결과를 확인한다.

캡처는 검증 도구다. 매핑 도구가 아니다.

함정 — context 응답이 너무 클 때

get_design_context 응답은 노드가 깊으면 60KB 가까이 나온다. MCP tool 응답이 토큰 한계를 넘으면 파일로 저장되기도 한다. 그 파일을 끝까지 다 읽어야 한다. 일부만 읽고 추측하면 캡처 보고 짜는 거랑 똑같아진다.

청크로 끊어 읽되 마지막 청크까지 도달했는지 확인. 게을러지면 같은 함정으로 돌아간다.

디자인 받을 때 확인할 항목 체크리스트

캡처만 보고 시작하지 않기 위해 get_design_context 응답에서 다음 항목을 표로 정리한다. 하나라도 비어 있으면 매핑을 시작하지 않는다.

Spacing

  • 화면 좌우 outer padding (보통 16/20pt)
  • 카드/섹션 내부 padding (좌우, 상하 각각)
  • 카드 사이 갭 vs 디바이더 (둘 중 무엇인지 명확히)
  • 아이콘과 텍스트 사이 간격

Color

  • 배경색 hex
  • 텍스트 색 hex (primary / secondary 구분)
  • 디바이더 hex (#F2F2F2 같은 옅은 색은 디자인 토큰 색과 다르게 보임)
  • 강조색·상태색 hex

Typography

  • font name (시스템 폰트인지 커스텀인지)
  • font size (pt)
  • font weight
  • line height

Shape

  • border radius (카드/버튼 별)
  • 디바이더 두께 (0.5pt / 1pt 구분)
  • 아이콘 size (size-[20px] 식으로 명시되어 있음)

구조

  • 카드 사이 구분이 갭인지 라인인지
  • child 노드 계층 (Stack 구조와 매칭)
  • 반복 요소가 같은 컴포넌트인지 서로 다른 노드인지

이 표가 다 채워진 다음에야 코드 한 줄을 짠다. 표 채우다가 빈 칸이 보이면 캡처 보고 추측하지 말고 get_design_context를 다시 호출하거나 응답을 끝까지 다 읽는다.

메모

  • 캡처는 검증 도구다. 매핑 도구가 아니다.
  • 디자인 매핑은 raw 정보로 시작한다. 색 hex, padding 값, font 이름과 크기까지.
  • 단편 패치 로테이션에 빠지면 멈춰라. 처음으로 돌아가서 전체 raw 정보를 다시 받는다.
  • Figma MCP 응답이 크면 끝까지 다 읽는다. 일부만 읽고 추측하면 시작 안 한 것과 같다.
  • “그럴듯한데 정답은 아닌” 결과가 가장 위험하다. 본인은 다 한 것 같은데 디자이너가 한눈에 안다.
